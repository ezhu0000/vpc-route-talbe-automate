当前现状：
PixVerse用了DX + Transit Gateway (TGW) 做多 VPC 互联，但发现：
- TGW 连接建好了，BGP 线路也建连了
- 但 VPC 之间还是不通
- 原因是每个 VPC 的子网路由表还需要手动配置指向 TGW 的路由
- PixVerse预期像阿里云 CEN 那样 —— BGP 自动放通，不需要手动改每个 VPC/子网的路由表
两云差异
AWS TGW 和阿里云 CEN 的关键区别
暂时无法在飞书文档外展示此内容
这就是差异 — AWS 的 TGW 只管自己内部的路由传播，但 VPC 侧的路由表不会自动更新。
在阿里云 CEN 的架构下，BGP 路由会自动下发到每个 VPC 的路由表，所以专线建连后就自动通了。
AWS 的设计理念不同 —— TGW 内部的路由传播是自动的（BGP 学到的路由会自动出现在 TGW 路由表里），但 AWS 出于安全考虑，不会自动修改 VPC 的路由表。这意味着 VPC 侧需要显式添加一条指向 TGW 的路由。
这不是 AWS 的缺陷，而是设计选择 —— 防止路由被意外注入导致安全问题。AWS 的大客户基本都是这么处理的。

方案四：批量导入导出（一次性）
导出某个已配好的路由表 
aws ec2 describe-route-tables --route-table-ids rtb-xxx \
  --query 'RouteTables[0].Routes[?GatewayId==tgw-xxx]' 
 
批量写入其他路由表 
for rtb in rtb-aaa rtb-bbb rtb-ccc; do
  aws ec2 create-route --route-table-id $rtb \
    --destination-cidr-block 10.0.0.0/8 \
    --transit-gateway-id tgw-xxx 
done 




实操建议
对PixVerse来说，方案二 + 方案三组合最合理：
1. 先用大网段路由解决现有 VPC 的互通问题（立竿见影）
2. 再搭一个 Lambda 自动化，让后续新增的 VPC 自动配好路由，这样体验上就接近阿里云 CEN 了。
针对目前 80 +路由表的情况，我们建议分两步走（AWS+Partner支持）：
第一步：批量配置，一次解决
不需要一条一条加精确路由。只需要在每个 VPC 的子网路由表里添加一条大网段路由（比如 10.0.0.0/8）指向 TGW。我们可以提供一个脚本，几秒钟批量完成所有路由表的配置，不需要手动操作。
而且这样做有一个好处：后续 IDC 侧新增网段，VPC 路由表也不需要再改，因为大网段已经覆盖了。
第二步：自动化，后续零运维
我们可以帮你们部署一个自动化方案 —— 用 EventBridge + Lambda 监听新 VPC 或新路由表的创建事件，自动注入指向 TGW 的路由。这样后续扩展 VPC 时，路由会自动配好，体验上和阿里云就基本一致了。
其他Q&A
Q：大网段路由会不会影响 VPC 内部通信？
A：不会。AWS 路由表遵循最长前缀匹配，VPC 本地路由（比如 10.1.0.0/16 local）优先级永远高于大网段路由。只有目的地不在本 VPC 内的流量才会走 TGW。
Q：这种做法是 workaround 吗？
A：不是，这是 AWS 官方推荐的最佳实践。AWS Well-Architected Framework 和官方文档里都建议用汇总路由（Summary Route）配合 TGW 使用。
Q：安全上有没有风险？
A：可以配合 TGW 路由表的关联和传播策略、以及安全组/NACL 做精细控制。大网段路由只是解决了"流量往哪走"的问题，"允不允许通"还是由安全组和 NACL 控制。
